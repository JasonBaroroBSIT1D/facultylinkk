## 6. Existing FacultyLink aggregation behavior

### 6.1 `kra_document_aggregate._legacy_aggregate_criterion_from_documents`

Used for **`kra1-c`** (and non-adapter `kra1-b`):

1. For each document with `effective_document_points(doc)`, group by **`indicator_id`** (fallback `public_id`).  
2. Keep **only the highest** point value **per indicator key**.  
3. **Sum** those per-indicator bests.  
4. Apply **`min(total, max_pts)`** where `max_pts` is published Criterion C max (**10**).

**Example conflict:** Two eligible UT adviser accomplishments (`kra1-c-adviser-ut`, 5 pts each) → system counts **5**, not **10**, before cap.

### 6.2 `rank_simulation_engine.py`

Calls `aggregate_criterion_documents(profile, "kra1", "kra1-c")` → same legacy path. KRA I total adds Criterion C estimate into KRA I alongside SET/SEF (A) and Criterion B.

### 6.3 `cap_kra1_instruction_total` (`criterion_b_scoring.py`)

Applies **`min(criterion_c_points, kra1-c max)`** then KRA I **100** ceiling — consistent with official **criterion** cap **if** the input `criterion_c_points` is correct.

### 6.4 `web/js/rules.js`

- Mirrors Annex A **point values** and evidence text.  
- Global condition mirrors **Item 8** double-counting rule (document across indicators).  
- Does **not** define aggregation algorithm (implementation is backend legacy aggregate).

### 6.5 Document-level points

`document_evidence_points.effective_document_points()` may use `verified_points`, `reviewer_score`, `estimated_points`, or OCR **provisional** scores — **without** Criterion C eligibility gates (completion, RRPA, mentorship rules).

**Conclusion:** Legacy **best-per-indicator-id** aggregation **conflicts** with Annex A **“for every service rendered”** as interpreted in §3 (Scenarios A, B, D). Criterion **cap at 10** is implemented; **per-service summation** is **not**.

## 7. Recommended scoring policy

### Recommendation: **Option A — Per-service accumulation** (with dedupe and human gates)

**Policy statement (proposed for FacultyLink, pending approval):**

> Sum **eligible, distinct** research-related and mentorship **services** that meet Section 15 and Annex A requirements, each credited at the published Annex A points for that role and project type, then apply **`min(sum, 10)`** for Criterion C.

**Evidence supporting Option A (not “easier code”):**

| Evidence | Page |
|----------|------|
| “**For every service rendered**” (research and mentorship) | 77–78 |
| **Max = 10** on criterion (not “max per row once”) | 10, 77 |
| Per-service point matrix (3/5/8/10 etc.) | 77 |

**Why not Option B (best-per-indicator):**

- **Not** stated in the circular.  
- **Under-counts** common cases (Scenarios A, B, D) relative to “every service” wording.  
- FacultyLink’s nine indicator IDs are **product codes**, not an official “one claim per ID” rule.

**Option C (alternative):** None identified that fits the PDF better than Option A without contradicting “for every service rendered.”

### 7.1 Proposed duplicate-prevention rules (implementation-time)

| Rule | Basis |
|------|--------|
| **One credit per distinct service instance** — dedupe key e.g. hash(student id/name + project title + role + term/date on approval sheet) | Prevents duplicate uploads; aligns with one approval sheet per service (Annex A p. 77) |
| **Same physical document** cannot support two indicators | Art. III item 8 p. 3 |
| **Adviser + panel same thesis** — **block second role** OR **flag for reviewer** until SUC policy clarifies | **UNCLEAR** officially — default **flag**, not auto-allow both |
| **Mentorship** — one claim per distinct competition outcome / team / award cycle | “For every service rendered” + evidence set p. 78 |
| Do **not** auto-enforce **5 students/AY** as hard reject | §15.1.a wording is **general**, not “shall” |

### 7.2 Historical scores

- **Do not retroactively change** stored `verified_points` / reviewer decisions without an approved **legacy policy** (mirror Criterion B grandfather approach).  
- Document whether pre-fix simulation totals remain until re-review or are recalculated only on new assessments.

### 7.3 Impact on surfaces

| Surface | Impact if Option A adopted |
|---------|---------------------------|
| **Faculty Mobile** | One **accomplishment** per service (student/project/role); multiple UT advisories = multiple claims |
| **Reviewer Web** | Per-service checklist (approval sheet, RRPA); assessment ≤ row points; running **room under 10** |
| **Rank Simulation** | Replace legacy **best-per-indicator** for `kra1-c` with **sum + cap 10**; optional C adapter like B |
| **Admin** | Published indicator points remain **per-service rates**, not “criterion totals” |
